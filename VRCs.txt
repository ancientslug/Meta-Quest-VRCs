====================================================================================================
Introduction
====================================================================================================

This document lists the Virtual Reality Check (VRC) requirements used to validate a Meta Quest
application before it is submitted to the Meta Horizon Store. Each entry states whether the check is
required, its priority, what it verifies, how to perform the test, and the expected result.

Meta’s own naming is “Virtual Reality Check” — a single check — with “VRCs” as the plural. The set
as a whole is presented as a checklist, but no individual entry is called a “checklist”.

How to use this document
------------------------

1. Read Test Environment Setup once per test machine and per headset.
2. Fill in the Applicability triage for the build under test. It tells you which of the 80 checks
   apply.
3. Follow the Recommended test-pass workflow, which orders the applicable checks so that the
   45-minute play sessions are shared rather than repeated.
4. Record every result on the Results record and every failure on the Issue report template.

The Quick reference table lists every check with its Requirement, Priority and the condition under
which it applies.

Platform assumption
-------------------

All procedures and commands in this document assume a Windows test machine. Commands use findstr,
setx, the CMD address-bar shortcut and PowerShell. They are not written for macOS or Linux.

Requirement
-----------

- Required — the application must pass this check to be approved for submission.
- Recommended — a best practice. It is checked only where the relevant feature is supported and will
  not, on its own, cause a submission failure.

Priority
--------

High, Mid, or Low indicates the relative importance and severity of the check when planning and
reporting test coverage. Priority is an internal planning field and does not override the
Requirement field: a Recommended check never causes a submission failure, whatever its priority.

Placeholders
------------

Text shown in square brackets — for example [PACKAGE.NAME], [FOLDER.NAME], [USERNAME],
[OBB FOLDER NAME], [DEVICE.NAME], and [LOG NAME] — must be replaced with the actual value for the
application or device under test.

VRC numbering
-------------

VRC numbers are not always consecutive (for example, Performance jumps from 1 to 3). The gaps
correspond to checks that Meta has retired or merged in earlier revisions and are intentionally
omitted. The retired numbers in the current Quest set are Performance.2, Functional.8,
Functional.11, and Input.6.

Currency of this document
-------------------------

VRC criteria are revised periodically and several have changed materially in recent revisions —
notably the frame rate and refresh rate requirements in Performance.1 and the supported SDK levels
in Packaging.4. Before relying on this document for a submission, confirm the current criteria
against the Meta Quest Virtual Reality Check (VRC) guidelines on the Meta Horizon OS developer site.
The version and date of this document are shown on the title line; update them whenever criteria are
changed.

Common Procedures
-----------------

Many tests share the same setup — connecting to the headset over ADB, pulling the application
package, viewing the Store cover art, and so on. To avoid repeating these steps in every test, they
are defined once in the Common Procedures section and referenced by letter (A–F) from the individual
test cases. A reference is shown like this:

→ Connect the headset over ADB — see Common Procedure A.

The reference is the whole instruction. The procedure’s steps are not restated in the test case, so
a change to a procedure is made in one place only.

Test Environment Setup
====================================================================================================

Everything in this section is prerequisite to the Common Procedures and test cases that follow.
Complete it once per test machine and per headset. All procedures assume a Windows test machine (see
Platform assumption).

Essential tools
---------------

Install Android Studio, which supplies ADB and the build tools used throughout this document:
https://developer.android.com/studio

After installation, the tools are found at the following paths. Substitute your own username, and
check the build-tools version number against what is actually installed — the folder is versioned
and will change as you update the SDK.

Tool                        Path
--------------------------  -------------------------------------------------------------------
platform-tools folder       C:\Users[USERNAME]\AppData\Local\Android\Sdk\platform-tools
apksigner.bat, aapt, aapt2  C:\Users[USERNAME]\AppData\Local\Android\Sdk\build-tools\36.1.0
apksigner.jar               C:\Users[USERNAME]\AppData\Local\Android\Sdk\build-tools\36.1.0\lib

For convenience, copy aapt, aapt2, apksigner.bat, and apksigner.jar into your platform-tools folder.
Every command in this document assumes it is run from there.

The Java Development Kit must be installed to complete VRC.Quest.Packaging.2:
https://www.oracle.com/java/technologies/downloads/#jdk26-windows

Set the JAVA_HOME variable from an administrator command prompt, matching the path to the JDK
version you actually installed:

    setx /m JAVA_HOME "C:\Program Files\Java\jdk-25.0.2"

The OVR Metrics Tool is required for the performance checks. Installation is described once, in
Common Procedure D; the Store listing is
https://www.meta.com/experiences/ovr-metrics-tool/2372625889463779/

→ Sideloading an archived build of the OVR Metrics Tool (for example v1.6.5, archived at
https://archive.org/details/ovr.metrics.tool.v1.6.5) is a fallback for older headsets only. Prefer
the Store version: an archived build is unversioned against current Horizon OS and may report stats
incorrectly.

Meta Horizon developer access
-----------------------------

Meta allows any account to be granted developer access by creating or joining an Organization on the
developer dashboard.

1. Create or log in to your Meta account.
2. Navigate to the developer dashboard (https://developer.oculus.com/manage/organizations/create/)
   and create an Organization, using a project codename rather than the shipping title if the
   project is confidential.
3. Once created, select Members.
4. Select Invite Members.
5. Invite every account that needs to enable Developer mode on a headset.

An account must belong to an Organization before Developer mode can be enabled on a headset.

Enabling Developer mode
-----------------------

The short form of this procedure is step 1 of Common Procedure A. The full form below includes a
factory reset, which is needed when the headset is being moved to a different test account — for
example before an entitlement check.

1. Install the Meta Horizon application on a smartphone.
2. Factory reset the headset if it is currently paired to another account. With the headset turned
   off, hold volume down and the power button to open the debug menu.
3. Select Factory Reset and proceed to wipe the headset.
4. Log in to the phone application with your testing account.
5. Pair by following the steps on screen.
6. Enable Developer mode through the phone application: Menu > Devices > [select your headset] >
   Developer mode > enable.

→ The volume-down-plus-power debug menu is the only way to factory reset a headset you cannot sign
in to. Note it before you start an entitlement check, since that test requires a reset partway
through.

Using wireless ADB
------------------

Wireless ADB frees the headset from the USB cable, which matters for roomscale and locomotion
testing. Set it up over USB first.

1. Connect the headset to your PC using a USB cable.
2. Obtain the headset’s IP address: adb shell ip route
3. Switch ADB to TCP mode: adb tcpip 5555
4. Connect over the network: adb connect [HEADSET'S IP ADDRESS]:5555
5. Disconnect the USB cable from the PC.
6. Confirm the headset is now listed wirelessly: adb devices

To disconnect: adb disconnect [HEADSET'S IP ADDRESS]:5555

→ Disabling Wi-Fi — whether through headset Settings or the svc wifi disable command — drops the
wireless ADB session and any tooling running over it, including the PowerShell toolkit in Appendix
A. Use a USB connection for the disconnect test in VRC.Quest.Functional.7. This warning is stated
here only; Functional.7 and Appendix A refer back to it.

Capturing evidence
------------------

Screenshots and video are how test failures get reported. Both are captured over ADB and land in
your platform-tools folder.

To take a screenshot:

→ Connect the headset over ADB — see Common Procedure A.

1. Run the command below. The screenshot is pulled automatically.

    adb exec-out screencap -p > [IMAGE NAME].png

To record video:

→ Connect the headset over ADB — see Common Procedure A.

1. Start recording: adb shell screenrecord /sdcard/[VIDEO NAME].mp4
2. Stop recording with Ctrl + C.
3. Pull the video from the headset: adb pull /sdcard/[VIDEO NAME].mp4

→ screencap writes PNG data, so name the output file .png. Naming it .jpg produces a file that is
still a PNG internally and that some issue trackers will reject.

→ The PowerShell toolkit captures a screenshot by writing to /sdcard/screenshot.png and pulling it,
and stops a recording with pkill -2 screenrecord. Both routes produce the same files; use whichever
is convenient.

Sideloading applications
------------------------

Test builds are installed directly rather than through the Store. This is the single description of
sideloading; Common Procedure A and VRC.Quest.Security.1 refer to it.

→ Connect the headset over ADB — see Common Procedure A.

1. Move the build .apk to your platform-tools folder.
2. Install the build: adb install [BUILD NAME].apk
3. If the build uses expansion files, push the OBB folder to the headset: adb push [OBB FOLDER NAME]
   /sdcard/Android/obb
4. Find the application under Library > Unknown Sources.

→ A sideloaded application does not always appear in Unknown Sources immediately. If it is missing,
restart the headset before assuming the install failed.

→ /sdcard/Android/obb and /storage/emulated/0/Android/obb are the same location; the PowerShell
toolkit uses the longer form. Android paths are case-insensitive on this partition, so
sdcard/android/obb also resolves.

To remove a build between test passes:

    adb shell sh -c 'cmd package list packages -3'
    adb uninstall [PACKAGE.NAME]

Common Procedures
====================================================================================================

Each procedure is defined once here. Test cases reference them by letter and do not restate their
steps.

A. Standard ADB Connection
--------------------------

1. Enable Developer mode: in the Meta Horizon phone app, go to Menu > Devices > [select your
   headset] > Developer mode > enable. (First-time setup, including Organization membership and
   factory reset, is under Test Environment Setup.)
2. Connect the headset to your PC via USB.
3. Open your platform-tools folder.
4. In the folder’s address bar, type CMD and press Enter to open a command window.
5. In the command window, run adb devices.
6. Put on the headset and accept the two authorization prompts that appear.

To install a test build after connecting, follow Sideloading applications under Test Environment
Setup.

B. Pulling the base.apk File
----------------------------

Requires the Standard ADB Connection (Procedure A). List the installed third-party packages to
identify [PACKAGE.NAME], resolve its folder, then pull the package:

    adb shell sh -c 'cmd package list packages -3'
    adb shell pm path [PACKAGE.NAME]
    adb pull /data/app/[FOLDER.NAME]/base.apk

C. Pulling the Android Manifest
-------------------------------

Requires base.apk (Procedure B) and aapt2 in your platform-tools folder. Export the manifest to a
text file and open it to inspect values:

    aapt2 dump xmltree base.apk --file AndroidManifest.xml > AndroidManifest.txt

Value encodings you will see in the manifest:

Value  Encoding
-----  ---------------------
True   (type 0x12)0xffffffff
False  (type 0x12)0x0
Auto   (type 0x10)0x0

D. OVR Metrics Tool Setup
-------------------------

This is the single description of installing and configuring the OVR Metrics Tool. Install it from
the Store where possible; sideload it only if you need a specific older build (see the note under
Essential tools).

Store install (all current headsets — Quest 2, Quest 3, Quest 3S, and Quest Pro):

1. Install the OVR Metrics Tool from
   https://www.meta.com/experiences/ovr-metrics-tool/2372625889463779/
2. In the headset, go to Library > OVR Metrics Tool.
3. Open Options, enable “Enable Persistent Overlay” and “Record all captured metrics to csv files”,
   then select the Advanced stats option.
4. Launch the application and begin testing.
5. When finished, close the application and pull the performance log:

    adb pull sdcard/Android/data/com.oculus.ovrmonitormetricsservice/files/CapturedMetrics

Sideload install (if you need a specific build):

1. Complete the Standard ADB Connection (Procedure A).
2. Download the build (v1.6.5 is archived at https://archive.org/details/ovr.metrics.tool.v1.6.5),
   add the .apk to your platform-tools folder, and install it, substituting the filename of the
   build you are installing: adb install OVRMetricsTool_v1.6.5.apk
3. In the headset, go to Library > Unknown Sources > OVR Metrics Tool.
4. Configure Options and pull the log as described above.

E. OVR Metrics Tool — Manual ADB Commands
-----------------------------------------

These commands drive the OVR Metrics Tool without the in-headset menu. The matching disable commands
are listed in the Command Reference.

Open OVR Metrics Tool:

    adb shell am start omms://app

Enable overlay:

    adb shell am broadcast -n com.oculus.ovrmonitormetricsservice/.SettingsBroadcastReceiver -a com.oculus.ovrmonitormetricsservice.ENABLE_OVERLAY

Enable Render Scale graph:

    adb shell am broadcast -n com.oculus.ovrmonitormetricsservice/.SettingsBroadcastReceiver -a com.oculus.ovrmonitormetricsservice.ENABLE_GRAPH --es stat render_scale

Record metrics to CSV:

    adb shell am broadcast -n com.oculus.ovrmonitormetricsservice/.SettingsBroadcastReceiver -a com.oculus.ovrmonitormetricsservice.ENABLE_CSV

Disable overlay:

    adb shell am broadcast -n com.oculus.ovrmonitormetricsservice/.SettingsBroadcastReceiver -a com.oculus.ovrmonitormetricsservice.DISABLE_OVERLAY

Enable the SpaceWarp frame rate graph (used when the application employs Application SpaceWarp):

    adb shell am broadcast -n com.oculus.ovrmonitormetricsservice/.SettingsBroadcastReceiver -a com.oculus.ovrmonitormetricsservice.ENABLE_GRAPH --es stat spacewarped_frames_per_second

F. Viewing the Store Cover Art
------------------------------

Several Store Asset checks require you to view the two cover art images.

1. Install the Meta Horizon application on a smartphone (for example from Google Play) and log in to
   an entitled Meta Horizon account.
2. To view the square Cover Art image, select the Menu tab, then select My Library.
3. To view the rectangular landscape Cover Art image, select the Search tab and search for the
   title.

The Hero Art banner is a third, separate image viewed on the web Store page
(https://www.meta.com/experiences/); see VRC.Quest.Asset.4.

Device matrix

VRC.Quest.Performance.1
~~~~~~~~~~~~~~~~~~~~~~~

Requirement: Required. Priority: High.

Description. The application must run at an allowed refresh rate and maintain a rendering rate of at
least 60 fps.

- Interactive applications must use a refresh rate of 72 Hz, 80 Hz, 90 Hz, 96 Hz, 100 Hz, or 120 Hz.
  Not all of these rates are available on every device.
- Media applications may use 60 Hz on devices that support it.
- Applications must maintain a rendering rate of at least 60 fps, subject to the Application
  SpaceWarp exception below.

Application SpaceWarp (AppSW) exception: interactive applications may run at half the refresh rate —
for example 36 fps at 72 Hz, or 30 fps at 60 Hz — for the portions of the experience that use
Application SpaceWarp. To qualify, the application must generate motion vectors that minimize
SpaceWarp artifacts.

Other exceptions: the rendering rate does not need to be maintained while a loading screen or
full-screen fade is present, while a system menu overlay is present, or while the session is being
streamed or recorded to video, since capture incurs additional GPU cost.

Steps to test.

→ Set up the OVR Metrics Tool and enable the required overlay and graphs, then pull the performance
log — see Common Procedure D, and the manual overlay commands in Common Procedure E.

1. Use the application for the length of the content or 45 minutes, whichever is shorter. (This
   session is shared with Performance.4, Functional.1 and Functional.6; see the Recommended
   test-pass workflow.)
2. Open the OVR Metrics Tool and select the log file for the application.
3. Observe the FPS graph and identify any extended periods below 60 fps.
4. Where the application uses Application SpaceWarp, enable the SpaceWarp frame rate graph and apply
   the half-rate threshold instead.

Expected result. The application does not experience extended periods of rendering below 60 fps, or
below 30 fps where Application SpaceWarp is in use, other than during the exceptions listed in the
description.

Notes. This criterion was relaxed in a 2024 revision. Earlier versions of this document required a
flat 72 fps; that figure is now a floor on the refresh rate for interactive applications, not a
target for the rendering rate.

The Quest technique is Application SpaceWarp (AppSW), which the application opts into by submitting
motion vectors and a depth buffer. It is distinct from Asynchronous SpaceWarp (ASW), the
runtime-driven PC-VR technique. The OVR Metrics Tool stat identifier is
spacewarped_frames_per_second in both cases.

Reading the overlay: watch the Average FPS graph. Where the application uses SpaceWarp, enable the
SpaceWarp FPS graph (Common Procedure E) and treat it as the Average FPS. With SpaceWarp engaged,
Average FPS shows half the refresh rate — for example 36 fps at 72 Hz — and SpaceWarp FPS shows the
full refresh rate. When SpaceWarp is not engaged, SpaceWarp FPS shows 0.

VRC.Quest.Security.1
~~~~~~~~~~~~~~~~~~~~

Requirement: Recommended. Priority: High.

Description. The application should perform a Platform entitlement check within 10 seconds of
launch. The purpose of the entitlement check is to ensure that an application is not usable without
being obtained through the Meta Horizon Store. On an unentitled account the application should
display a prompt and then close, and it should do both within 10 seconds of launching rather than
leaving the user waiting.

Steps to test. Requirements: one Meta Horizon account with the application’s entitlement and dev
mode enabled, and one Meta Horizon account without the application’s entitlement and dev mode

VRC.Quest.Input.1
~~~~~~~~~~~~~~~~~

Requirement: Recommended. Priority: Mid.

Description. The in-application menu should be opened by pressing the Menu button on the left Touch
controller, or the menu button on a gamepad where the application supports one.

1. Launch the application.
2. Enter gameplay.
3. Press the Menu button on the left Touch controller.

VRC.Quest.Input.2
~~~~~~~~~~~~~~~~~

Requirement: Recommended. Priority: Mid.

Description. When picking up objects within the application, the Touch controller’s Grip button
should be used rather than the Trigger button.

Steps to test.

1. Launch the application.
2. Enter gameplay.
3. Attempt to pick up an object.

VRC.Quest.Input.3
~~~~~~~~~~~~~~~~~

Requirement: Recommended. Priority: Mid.

Description. In-application hands and controllers should line up with the user’s real-world
counterparts in position and orientation as closely as possible. It should appear as if the user’s
hands are moving in a VR space.

Steps to test.

1. While using the application, hold your hands in front of your face and raise the headset slightly
   so you can compare your real-world hands and your virtual hands.
2. Repeat with your hands at different angles and positions to observe any disparities.

Expected result. In-application hands and controllers match the user’s real-world hands in position
and orientation.

VRC.Quest.Input.4
~~~~~~~~~~~~~~~~~

Requirement: Required. Priority: High.

Description. Applications must be focus-aware. A focus-aware application continues rendering when it
loses focus, hides its own hand and controller models, and ignores all input while the Horizon OS
menu is open.

Steps to test.

1. Launch the application and enter gameplay.
2. Press the Meta button on the right Touch controller.
3. Observe whether the application continues to render behind the Horizon OS menu.
4. Attempt to interact with the application while the menu is open.

Expected result. The application continues to render in the background, its own hand and controller
models are hidden while the system’s own hands or controllers for the Horizon OS menu appear
instead, and the user can interact only with the Horizon OS menu.

Notes. If the Horizon OS menu appears on top of the running and rendering application, it is
configured to be focus-aware. If a system-provided environment appears instead, the application is
not focus-aware.

VRC.Quest.Input.5
~~~~~~~~~~~~~~~~~

Requirement: Recommended. Priority: Mid.

Description. For applications that support hand tracking, hands must be rendered in the correct
position and orientation and must animate correctly.

Steps to test.

1. Look in and out of the headset to check that the in-VR hands match your hands in position and
   orientation.
2. Observe whether the in-VR hands animate appropriately and with correct movement.

Expected result. In-VR hands render correctly and keep up with user movement.

VRC.Quest.Input.7
~~~~~~~~~~~~~~~~~

Requirement: Required. Priority: High.

Description. For applications that support hand tracking, the application must properly respect when
input is switched between controllers and hands.

Steps to test.

1. In Settings > Device, enable Auto Enable Hands or Controllers.
2. Launch the application.
3. Switch back and forth between hands and controllers several times by picking up and setting down
   the controllers.
4. Observe that the application switches appropriately and continues to function.

Expected result. The application does not experience any functional or rendering issues when
switching between hand tracking and controllers.

VRC.Quest.Input.8
~~~~~~~~~~~~~~~~~

Requirement: Required. Priority: High.

Description. For applications that support hand tracking, the system gesture is reserved and should
not trigger any other action within the application.

Steps to test.

1. Within the application, hold your hand up with an open palm toward the headset.
2. Pinch your thumb and index finger together to perform the system gesture.
3. Observe whether any in-application action is triggered alongside the Quick Actions Menu.

Expected result. Only the system gesture is processed. No other gesture events are processed.

Notes. Look at your palm and pinch your thumb and index finger together to access the Quick Actions
Menu. Keep them pinched to navigate the menu; to select an item, highlight it and un-pinch your
fingers.

VRC.Quest.Ads.1
~~~~~~~~~~~~~~~

Requirement: Required. Priority: High.

Description. The application must meet all advertising policy requirements.

Steps to test.

1. Launch the application and progress through content until advertisements are encountered.
2. Record every advertisement placement, format, and offer promoted.
3. Assess each against the Application Advertising Policy below.
4. Compare the content of each advertisement against the content rating declared for the
   application.

Expected result. The application meets the Application Advertising Policy requirements.

Notes — Application Advertising Policy.

- Advertisements must be age appropriate. Advertisements and their associated offers — for example,
  an advertisement promoting the download of another application — must be appropriate for the
  content rating of your application.
- Advertisements must not contain sexually explicit content, even if not rising to the level of
  pornography, and even where such content may otherwise be allowed under the Content Guidelines.
- Advertisements must not promote unsafe substances (including recreational drugs), weapons,
  ammunition or explosives, tobacco and related products, alcohol, online gambling, or CBD and
  related products.
- Advertisements should not portray adults or children in unsafe situations or condone unsafe
  behaviour.
- Advertisements must not imitate or impersonate system features or services, or interfere with the
  main function of the application or normal system and device operation.
- Advertisements must include proper disclosures and cannot be disguised as editorial content.
  Disclosure requirements can vary by jurisdiction.
- Advertisements, and the products they represent, must meet the Content Guidelines.
- In-application advertisements must only promote content appropriate for the age of the
  application’s intended audience.
- In-application advertisements, in applications intended for children, must not appeal to
  gullibility or promote unhealthy behaviour in any way.

====================================================================================================
Supplementary Checks
====================================================================================================

The checks in this section are not VRCs. Meta does not test them at submission and they cannot cause
a submission failure. They are included because they surface problems that later fail a VRC, or
because they are commonly requested alongside it. Record them separately from the VRC results so the
two are not confused; the Results record has a separate block for them.

Temperature check
-----------------

Requirement: Not a VRC. Priority: Mid.

Description. If the headset begins to feel too hot while testing, the application may be too
demanding for its processor, which usually means it is not correctly optimized for Meta Quest
hardware. The maximum safe temperature for any Meta Quest headset is 45 °C. If an application drives
the headset hotter than this, file an issue.

Steps to test.

1. Run the application for a sustained period — the length of the content or 45 minutes, whichever
   is shorter (shared with Performance.1).
2. If the headset feels hot to the touch, read the temperature: adb shell dumpsys battery | findstr
   "temperature"

Expected result. The headset stays at or below 45 °C throughout the test.

Notes. It is not necessary to check the temperature if the headset does not already feel hot to the
touch.

The command reports temperature in Celsius but omits the decimal point — a reading of 412 means 41.2
°C, not 412 °C. Divide by ten before recording the result. The PowerShell toolkit entry “Get headset
temperature” inserts the decimal point for you.

A thermal problem usually shows up as a Performance.1 failure first, since the device throttles
before it gets dangerously warm. Treat a hot headset as a lead to investigate rather than a finding
in itself.

Low battery state testing
-------------------------

Requirement: Not a VRC. Priority: Low.

Description. This check covers how an application behaves while the device is in a low battery
state, since Horizon OS reduces clocks under battery saver. It is not a required check and is only
performed on request.

Steps to test.

1. Simulate the low battery state:

    adb shell dumpsys battery set ac 0
    adb shell dumpsys battery set usb 0
    adb shell dumpsys battery set wireless 0
    adb shell dumpsys battery set level 1
    adb shell dumpsys battery unplug

2. Launch the application and exercise its core content.
3. Restore the device to its real battery state when finished:

    adb shell dumpsys battery reset
    adb shell settings put global low_power 0

Expected result. The application remains stable and does not lose data while the device reports a
low battery state.

Notes. Always run the reset commands before releasing the headset. A device left in a simulated
battery state will report wrong values to every subsequent test, including the temperature check,
which reads from the same dumpsys service.

Thermal throttling simulation
-----------------------------

Requirement: Not a VRC. Priority: Low.

Description. An application running above 72 Hz may be throttled by the system under thermal load:
first the refresh rate drops to 72 Hz, and if conditions worsen the frame rate is halved while the
refresh rate is held. This check confirms the application keeps working when that happens, without
waiting for the headset to heat up.

Steps to test.

→ Connect the headset over ADB — see Common Procedure A.

1. Launch the application and enter gameplay at its normal refresh rate.
2. Simulate throttling for 10 seconds:

    adb shell am broadcast -a com.oculus.vrruntimeservice.COMPOSITOR_SIMULATE_THERMAL --es subsystem refresh --ei seconds_throttled 10

3. Observe the application during and after the throttled period, with the OVR Metrics Tool overlay
   running (Common Procedures D and E).

Expected result. The application keeps running without crashing, freezing, or losing input while the
refresh rate drops, and recovers when the throttled period ends.

Notes. Only meaningful for applications that set a refresh rate above 72 Hz. Source: Meta’s Set
Display Refresh Rates
(https://developers.meta.com/vr/documentation/unreal/unreal-change-display-refresh-rate/) page. A
failure here is a lead for Performance.1 or Functional.1, not a finding in itself.

Resource usage profiling
------------------------

Requirement: Not a VRC. Priority: Low.

Description. When an application fails Performance.1 or Functional.1, these commands narrow down
where the cost is going. They are diagnostic aids for writing a useful bug report, not pass or fail
criteria.

Steps to test. Run the relevant command while the application is in the state that reproduces the
problem.

Measure        Command
-------------  --------------------------------------------------------
CPU usage      adb shell dumpsys cpuinfo \| findstr [PACKAGE.NAME]
Memory usage   adb shell dumpsys meminfo \| findstr [PACKAGE.NAME]
Thread usage   adb shell dumpsys activity [PACKAGE.NAME]
Battery usage  adb shell dumpsys batterystats \| findstr [PACKAGE.NAME]
Network usage  adb shell dumpsys netstats \| findstr [PACKAGE.NAME]

Expected result. No expected result — attach the output to the issue alongside the OVR Metrics log.
The PowerShell toolkit entry “Pull Performance overview” runs all of these plus gfxinfo framestats
and SurfaceFlinger in one pass and writes performance_metrics.txt.

Recording build and OS versions
-------------------------------

Requirement: Not a VRC. Priority: Mid.

Description. Every test result should record which build was tested and which Horizon OS version it
was tested against, so that a result can be reproduced or retired when either changes. This is Stage
0 of the Recommended test-pass workflow.

Steps to test. Capture all three values at the start of a test pass.

Value                     Command
------------------------  -------------------------------------------------------------------
Application version       adb shell dumpsys package [PACKAGE.NAME] \| findstr versionCode
Horizon OS shell version  adb shell dumpsys package com.oculus.vrshell \| findstr versionCode
Headset serial number     adb shell getprop ro.serialno

Expected result. All three values are recorded against the test pass, on the Results record.

Notes. The Oculus VR Shell versionCode is the practical proxy for the Horizon OS build. It matters
because several VRCs — focus awareness, passthrough launch behaviour, and the allowed refresh rates
— depend on OS behaviour that changes between versions. A result recorded without it cannot be
reproduced later.

    profiles, leaderboards, friends). An application that fails Security.1 or Privacy.2 may do so
    because the checkup was never completed.

Data Protection Assessment
    Where it is checked: Developer Dashboard, per organization
    Why it matters to a VRC pass: Required for applications that handle user data; Privacy.5 looks
    for incidents, this looks for controls.

Content rating (IARC)
    Where it is checked: Developer Dashboard, Submission Info > Content Ratings
    Why it matters to a VRC pass: All applications must be rated by IARC through a questionnaire on
    the IARC site. Applications released in South Korea also need a GRAC rating, which Meta issues
    automatically with the IARC certificate. Ads.1 and Content.1 compare advertisements and content
    against this rating, so an inaccurate rating fails them indirectly.

Comfort rating
    Where it is checked: Developer Dashboard submission metadata
    Why it matters to a VRC pass: Every application must be assigned one of three ratings:
    Comfortable (generally no camera movement, player motion, or disorienting effects; usually a
    fixed camera), Moderate (more camera and player motion), or Intense (first-person camera motion,
    acceleration, or significant camera and player motion). Content.2 requires metadata to match the
    experience.

Age group self-certification
    Where it is checked: Developer Dashboard, Meta Quest Developer Hub, or the Oculus Platform
    Utility
    Why it matters to a VRC pass: Mandatory for every application and separate from the IARC rating;
    an application cannot be published without it. Applications for mixed ages (under 13 and 13+)
    must implement the Get Age Category API. Users under 10 must be prevented from using the
    application. Streaming.4 and the children’s clauses of Ads.1 and Content.1 depend on the
    declared age group.

App Sharing
    Where it is checked: Meta App policies 3.4
    Why it matters to a VRC pass: Every submitted application must support App Sharing (secondary
    accounts on the headset launching the primary user’s purchases) unless Meta agrees otherwise in
    writing. Functional.12 is the test for this.

Permission to run ads
    Where it is checked: Meta App policies 2.1
    Why it matters to a VRC pass: Applications may not run ads without Meta’s express written
    agreement, except media-viewing (“windows into an existing service”) and social media
    applications. Ads that do not pause content may not take more than 40 % of the content panel,
    and ads that appear outside the panel are not allowed. An ordinary game showing ads breaks
    policy before Ads.1 to Ads.7 apply.

Official Meta test plan (.xls / .csv)
    Where it is checked: https://developers.meta.com/vr/resources/publish-quest-req/
    Why it matters to a VRC pass: Meta’s own tester steps, downloadable. Meta notes they are
    slightly out of date; use them as a cross-check, not a source of truth.

Common VRC failures guide
    Where it is checked: https://developers.meta.com/horizon/resources/publish-common-vrc-failures/
    Why it matters to a VRC pass: Lists the checks most often failed at review (Asset.2, Asset.5,
    Functional.2, Functional.7, Security.1, Security.2, Performance.1, Input.7). Weight test time
    toward these.

Sources for the rating, age-group, App Sharing and advertising rows: App policies
(https://developers.meta.com/vr/policy/app-policies/) (updated 2026-03-10) and Age group
self-certification and youth requirements
(https://developers.meta.com/horizon/resources/age-groups/) (updated 2026-04-02).

Platform, store, and submission
-------------------------------

Term                         Definition
---------------------------  -----------------------------------------------------------------------
VRC (Virtual Reality Check)  One of the validation requirements an application must meet before it
                             can be published to the Meta Horizon Store. Each VRC is marked Required
                             or Recommended and carries a priority. The plural is VRCs; the set as a
                             whole is presented as a checklist, but an individual entry is a check,
                             not a checklist.

Meta Horizon Store           Meta’s official distribution store for Quest applications, formerly the
                             Oculus Store.

Entitlement                  A record granting a user or the application the right to run a
                             purchased app or feature. Applications commonly perform an entitlement
                             check on launch to confirm the user owns the title.

Developer mode               A setting enabled through the Meta Horizon phone app that unlocks USB
                             debugging and sideloading on the headset. Required before ADB will
                             connect.

Unknown Sources              The area of the headset Library where sideloaded, non-store
                             applications appear.

Sideload                     Installing an application directly onto the headset, for example with
                             adb install, rather than through the Store.

Data Use Checkup             The Developer Dashboard certification that gates access to platform SDK
                             features; see Submission requirements outside the VRC list.

Tools and environment
---------------------

Term                                         Definition
-------------------------------------------  -------------------------------------------------------
ADB (Android Debug Bridge)                   The command-line tool for communicating with an
                                             Android-based device — the Quest runs Horizon OS, which
                                             is built on Android — over USB or Wi-Fi to install

platform-tools                               The folder from Google’s Android SDK containing adb and
                                             related utilities. The commands in this document are
                                             run from here.

aapt / aapt2 (Android Asset Packaging Tool)  Build tools used to inspect an APK’s contents and dump
                                             its manifest and badging metadata. aapt2 supersedes
                                             aapt for dumping the manifest and badging. aapt is

apksigner                                    The Android SDK tool that verifies, or applies, an
                                             APK’s cryptographic signature.

JDK (Java Development Kit)                   The Java toolchain required by some Android build
                                             tools, such as apksigner.

JAVA_HOME                                    The environment variable that tells tools where the JDK
                                             is installed.

logcat                                       Android’s system log stream. adb logcat captures
                                             runtime logs for debugging.

findstr                                      A Windows command-line utility used here to filter
                                             aapt2 output down to a specific field.

Term                                               Definition
-------------------------------------------------  -------------------------------------------------

                                                   feature the application relies on, such as head

Performance and rendering
-------------------------

Term                               Definition
---------------------------------  -----------------------------------------------------------------
Frame rate / rendering rate (fps)  How many rendered frames the application produces each second. VR
                                   requires a high, stable frame rate to stay comfortable. See
                                   VRC.Quest.Performance.1 for the current minimum.

Refresh rate                       How many times per second the headset display updates.
                                   Interactive applications must select one of 72, 80, 90, 96, 100,
                                   or 120 Hz; not every rate is available on every device. Media
                                   applications may use 60 Hz where supported.

OVR Metrics Tool                   Meta’s on-device utility that overlays and records performance
                                   metrics such as frame rate, GPU and CPU levels, and dropped
                                   frames.

Persistent Overlay                 An OVR Metrics Tool option that keeps the metrics overlay visible
                                   on top of any running application.

CapturedMetrics                    The folder of CSV logs the OVR Metrics Tool writes when metric
                                   recording is enabled.

Application SpaceWarp (AppSW)      The Quest technique in which the application submits motion
                                   vectors and a depth buffer so the runtime can synthesize
                                   intermediate frames, allowing it to render at half the refresh
                                   rate. This is the technique referenced by the Performance.1
                                   exception.

Asynchronous SpaceWarp (ASW)       The runtime-driven PC-VR equivalent, applied without application
                                   involvement. It is not the Quest technique, and the two should
                                   not be used interchangeably.

Render Scale                       A multiplier on the rendered resolution relative to the display.
                                   Higher values improve clarity but cost performance.

Latency                            The delay between a user’s input or movement and the matching
                                   on-screen response. High latency causes discomfort.

Judder                             The screen-stuttering effect caused by the view failing to keep
                                   up with head movement.

Interaction and tracking
------------------------

Term                              Definition
--------------------------------  ------------------------------------------------------------------
Head tracking                     The headset’s ability to track head position and orientation. The
                                  android.hardware.vr.headtracking feature flag marks an application
                                  as a true VR experience rather than a 2D one.

6DoF / 3DoF (degrees of freedom)  6DoF tracks both rotation and position, letting the user
                                  physically move around; 3DoF tracks rotation only. Quest headsets
                                  and Touch controllers are 6DoF.

Hand tracking                     Controller-free input that uses the headset cameras to track the
                                  user’s hands.

Controller                        The Touch controllers. Testing covers button mapping, tracking
                                  accuracy, and reconnection behaviour.

Passthrough                       Displaying the real-world camera feed inside the headset, used for
                                  mixed reality and boundary setup.

Boundary (Guardian)               The user-defined play-area boundary. Applications must respect it
                                  and warn the user appropriately.

Locomotion                        How the user moves through the virtual world — teleport, smooth
                                  movement, and so on — closely tied to comfort.

Comfort                           Design and testing considerations that reduce motion sickness,
                                  such as vignetting, snap turning, and a stable frame rate.

Spatial anchor                    A fixed real-world reference point that virtual content can be
                                  pinned to, persisting across sessions.

Focus-aware                       The behaviour that allows the Horizon OS menu to be opened while
                                  the application continues to render in the background, with its
                                  own hands and controllers hidden and its input ignored.

====================================================================================================
Official Hardware Terminology
====================================================================================================

When an application refers to headset or controller hardware — in on-screen text, imagery,
voice-over, tutorials, or button prompts — it must use Meta’s official names for those parts.
Unofficial, generic, or inconsistent labels (for example calling the Meta button a “home button”,
the trigger an “index trigger” in user-facing copy, or the grip button a “side button”) confuse
users, break accessibility read-out, and are a common source of review feedback.

→ Match the exact terms below. Where two names are officially accepted (Meta button / Oculus
button), either is valid — but stay consistent within a single application. Reference the layout for
the correct hand: the A and B buttons are on the right controller, X and Y on the left; swapping
them is a frequent mistake.

→ Layouts are described in words. Each description starts with an at-a-glance summary, then gives
positions in detail. Left and right on the controllers are the hand that holds them; left and right
on the headset are as worn, from the wearer’s point of view.

Touch controller buttons and inputs
-----------------------------------

Meta Quest Touch controllers are the standard 6DoF input devices. The core button names are the same
across controller generations (Meta Quest Touch, Touch Plus, and Touch Pro); what differs between
generations is tracking hardware and advanced sensing, not the button names.

At a glance: on the top face of each controller the thumbstick sits highest, with the system button
directly below it. The two face buttons run diagonally beside the system button, and the flat thumb
rest lies beyond them. The trigger is on the front of the handle under the index finger, and the
grip button is on the side of the handle under the middle finger.

Both controllers share the same physical arrangement, mirrored. On the top face, the thumbstick sits
highest. The system button — Menu on the left controller, Meta on the right — sits directly below
the thumbstick. The two face buttons are stacked diagonally beside the system button: the upper
button (Y on the left controller, B on the right) sits above and to the side of the lower one (X on
the left, A on the right). On Touch Plus controllers the flat thumb rest lies beyond the face
buttons. Touch Plus controllers have no tracking ring; the original Meta Quest Touch controllers
have a ring over the top face.

Neither the trigger nor the grip button is visible from the top face. The trigger is on the front of
the handle, angled to meet the index finger. The grip button is on the inner side of the handle —
the side facing the other controller — where the middle finger rests when the handle is held.

The single most useful thing to remember is which pair belongs to which hand: A and B are on the
right controller, X and Y on the left, and the upper button of each pair is the second letter
alphabetically. Swapping them is the most frequent labelling error in button prompts.

Control                         Controller  Official name and usage
------------------------------  ----------  --------------------------------------------------------

B button                        Right       Upper face button on the right controller.

Meta button (or Oculus button)  Right       The system button on the right controller. A short press
                                            opens the Navigator, or universal menu; press and hold
                                            to recentre the view. Both names are officially
                                            accepted; do not call it the “home” or “Oculus home”
                                            button.

X button                        Left        Lower face button on the left controller.

Y button                        Left        Upper face button on the left controller.

Headset parts and controls
--------------------------

Exact controls vary by model (Meta Quest 2, Quest 3, Quest 3S, and Quest Pro), so reference the
layout for the specific device under test. The official part names below apply across the current
Quest family.

At a glance, the front of the headset as worn: a camera pod at each outer edge with a smaller centre
module between them; the volume rocker and IPD adjustment along the underside; and, on Quest 3, the
USB-C port, power button, and status light grouped together on the left side.

Front of the headset. Three raised pills run across the front face: two camera pods at the outer
edges, flanking a smaller centre module which on Quest 3 houses the depth sensor. Along the
underside, the volume rocker sits toward one end and the IPD adjustment toward the other. On Quest 3
the power button and USB-C port are together on the left-hand side as worn, with the USB-C port
above the power button and the status light beside them.

Left and right on a headset are ambiguous unless you say from where. Throughout this document, left
and right mean as worn, from the wearer’s point of view. A drawing of the front face is mirrored
relative to that, so controls described here as being on the left will appear on the right of such a
drawing.

At a glance, the side that faces the user: two lenses side by side at the centre, the removable
facial interface surrounding them, and a strap arm snapped to each side of the headset, with the top
strap threaded through the front bracket.

User-facing side of the headset. Two circular lenses sit side by side at the centre, their
separation set by the IPD mechanism. Surrounding them is the facial interface, the removable foam
pad that contacts the brow, cheeks, and bridge of the nose, and which detaches for cleaning or to
fit a glasses spacer.

Part                           Official name and notes
-----------------------------  ---------------------------------------------------------------------
Power button                   Turns the headset on and off and wakes or sleeps it. Located on the
                               side of the headset; on Quest 3 it is on the left side as worn, below
                               the charging port.

Volume buttons                 The paired buttons — volume up and volume down — on the underside of
                               the headset that control the main volume.

USB-C port (charging port)     The USB-C connector used for charging and for a wired PC connection
                               (Meta Quest Link). On Quest 3 it sits on the left side as worn, above
                               the power button.

IPD adjustment                 The mechanism that sets lens separation to match the user’s
                               interpupillary distance (IPD). Quest 3 uses a continuous IPD wheel on
                               the underside; Quest 2 and Quest 3S use fixed positions. Correct IPD
                               is required for a clear image and for comfort.

Lenses                         The optical lenses the user looks through — pancake lenses on Quest 3
                               and Quest 3S. Keep them out of direct sunlight, which can permanently

Appendix A: walrusvr PowerShell Toolkit
====================================================================================================

A companion PowerShell script, walrusvr, wraps the commands in this document behind a menu, so that
the commands do not have to be retyped by hand. It presents 50 numbered entries in two columns and
runs the selected one, prompting for a package name or OBB folder where the command needs it. The
full listing appears in Appendix B.

Most entries are direct equivalents of commands in the Command Reference. The following do more than
wrap a single command and are the reason the script is worth using:

Entry                                     What it adds
----------------------------------------  ----------------------------------------------------------
List all permissions used (categorized)   Pulls the permissions from the manifest and sorts them
                                          into Prohibited, Restricted, and Other against the lists
                                          in VRC.Quest.Security.2. This turns a Security.2 pass or
                                          fail into a glance rather than a manual comparison against
                                          two long lists. It includes uses-permission-sdk-23 entries
                                          and matches each permission on its exact name, so a
                                          permission that only contains a listed name (for example
                                          horizonos.permission.HEADSET_CAMERA, which is not CAMERA)
                                          is not misreported as prohibited.

List all features used (categorized)      Sorts declared features into non-VR and other, and reports
                                          required and not-required features separately, which is
                                          the check behind VRC.Quest.Packaging.3 (the non-VR list is
                                          reproduced under that check). A feature counts as non-VR
                                          only when it matches a listed name or is a sub-feature of
                                          one, and features the build tools add automatically are
                                          marked (implied).

Get headset temperature                   Reads the raw dumpsys value and inserts the decimal point,
                                          so it reports 41.2 C rather than 412. This is the check
                                          described under Supplementary Checks.

Pull Performance overview                 Runs cpuinfo, meminfo, gfxinfo framestats, netstats,
                                          batterystats, SurfaceFlinger, and activity for one package
                                          in a single pass and writes the combined output to
                                          performance_metrics.txt. Useful as the attachment on a
                                          Performance.1 or Functional.1 issue.

base.apk file size check                  Reports the size in megabytes rather than the kilobyte
                                          block count that adb shell ls -s returns, which makes the
                                          1 GB limit in VRC.Quest.Packaging.5 directly readable.

Connect / disconnect headset to wireless  Resolves the headset IP from adb shell ip route
                                          automatically instead of requiring you to read it off and
                                          retype it.

Running the script
------------------

1. Save the listing in Appendix B as a file with a .ps1 suffix — for example, paste it into a .txt
   file and rename the file so its suffix is .ps1.
2. Place it in your platform-tools folder, or wherever adb and aapt2 live. The script will not
   function anywhere else, since it relies on those tools being on the path it sets.
3. Right-click the file and select “Run with PowerShell”.

If the window closes immediately
--------------------------------

This is an execution policy block, not a fault in the script.

1. Search for PowerShell in the Windows search bar.
2. Right-click and select Run as administrator.
3. Run the command below and answer yes to the prompt that appears: Set-ExecutionPolicy Unrestricted

→ Set-ExecutionPolicy Unrestricted lowers the execution policy machine-wide and leaves it lowered.
On a shared or general-purpose machine, prefer Set-ExecutionPolicy -Scope Process Bypass, which
applies only to the current PowerShell session and reverts when it closes.

Prerequisites
-------------

The script depends on the same environment described in Test Environment Setup. In particular:

- Android Studio must be installed, and aapt2 must be reachable from the folder the script runs in.
- The Java Development Kit must be installed for the APK signature verification entry to work. That
  entry hard-codes a JDK path; edit it to match the version you actually installed rather than
  relying on the value in the listing.
- The OVR Metrics Tool must be installed on the headset for the performance entries to return
  anything.
- Wireless ADB, if used, will drop when Wi-Fi is disabled — including by the script’s own
  disconnect-test entry. Run that entry over USB (see the warning under Using wireless ADB).

@{ "Description" = "List all permissions used (categorized)"
        "Command" = {
            # Includes uses-permission-sdk-23 entries. Each permission is matched on its exact
            # short name (the part after the last dot), so names that merely contain a listed
            # name - for example horizonos.permission.HEADSET_CAMERA or EXPAND_STATUS_BAR -
            # are not misreported as prohibited.
            $output = aapt2 dump permissions base.apk | Where-Object { $_ -match "^\s*uses-permission(-sdk-23)?: name='" } | ForEach-Object { $_.Split("'")[1] } | Sort-Object -Unique
            if ($output) {
                $prohibitedMatches = @(); $restrictedMatches = @(); $otherMatches = @()
                foreach ($permission in $output) {
                    $shortName = $permission.Split('.')[-1]
                    if ($prohibited -contains $shortName) { $prohibitedMatches += $permission }
                    elseif ($restricted -contains $shortName) { $restrictedMatches += $permission }
                    else { $otherMatches += $permission }
                }

                Write-Host "Prohibited: $($prohibitedMatches -join "`n")"
                Write-Host "Restricted: $($restrictedMatches -join "`n")"
                Write-Host "Other: $($otherMatches -join "`n")"
            } else {
                Write-Host "No permissions found." } } }

@{ "Description" = "List all features used (categorized)"
        "Command" = {
            # Reports required and not-required features separately. A feature counts as non-VR
            # when it equals a listed name or is a sub-feature of one (for example
            # android.hardware.touchscreen.multitouch), never on a partial-text match.
            # Features the build tools add automatically are marked (implied).
            $lines = aapt2 dump badging base.apk
            $required    = @($lines | Where-Object { $_ -match "^\s*uses-feature: name='" }              | ForEach-Object { $_.Split("'")[1] } | Sort-Object -Unique)
            $notRequired = @($lines | Where-Object { $_ -match "^\s*uses-feature-not-required: name='" } | ForEach-Object { $_.Split("'")[1] } | Sort-Object -Unique)
            $implied     = @($lines | Where-Object { $_ -match "^\s*uses-implied-feature: name='" }      | ForEach-Object { $_.Split("'")[1] })
            $isNonVR = { param ($feature) foreach ($name in $nonVR) { if ($feature -eq $name -or $feature.StartsWith("$name.")) { return $true } }; return $false }
            $label   = { param ($feature) if ($implied -contains $feature) { "$feature (implied)" } else { $feature } }

            if ($required.Count -gt 0 -or $notRequired.Count -gt 0) {
                $nonVRRequired    = $required    | Where-Object { & $isNonVR $_ }       | ForEach-Object { & $label $_ }
                $nonVRNotRequired = $notRequired | Where-Object { & $isNonVR $_ }       | ForEach-Object { & $label $_ }
                $otherRequired    = $required    | Where-Object { -not (& $isNonVR $_) } | ForEach-Object { & $label $_ }
                $otherNotRequired = $notRequired | Where-Object { -not (& $isNonVR $_) } | ForEach-Object { & $label $_ }

                Write-Host "Non-VR features (required): $($nonVRRequired -join "`n")"
                Write-Host "Non-VR features (not required): $($nonVRNotRequired -join "`n")"
                Write-Host "Other features (required): $($otherRequired -join "`n")"
                Write-Host "Other features (not required): $($otherNotRequired -join "`n")"
            } else {
                Write-Host "No features found." } } }

# Show menu
function Show-Menu {
    Clear-Host
    Write-Host "walrusvr"
    Write-Host "-------------------"
    $half = [math]::Floor($adbCommands.Count / 2)
    for ($i = 0; $i -lt $half; $i++) {
        Write-Host "$($i + 1). $($adbCommands[$i].Description)" -NoNewline
        Write-Host (" " * (40 - $adbCommands[$i].Description.Length)) -NoNewline
        if ($i + $half -lt $adbCommands.Count) {
            Write-Host "$($i + $half + 1). $($adbCommands[$i + $half].Description)"
        } else {
            Write-Host ""
        }
    }
    if ($adbCommands.Count % 2 -eq 1) {
        Write-Host "$($adbCommands.Count). $($adbCommands[-1].Description)"
    }
    $choice = Read-Host "Enter your choice"
    return $choice
}

function Run-ADBCommand {
    param ($index)
    $command = $adbCommands[$index].Command
    if ($command -is [scriptblock]) {
        if ($adbCommands[$index].Params) {
            $params = @{}
            foreach ($paramName in $adbCommands[$index].Params) {
                $paramValue = Read-Host "Enter $paramName"
                $params[$paramName] = $paramValue
            }
            & $command @params
        } else {
            & $command
        }
    } else {
        if ($adbCommands[$index].Params) {
            $params = @()
            foreach ($paramName in $adbCommands[$index].Params) {
                $paramValue = Read-Host "Enter $paramName"
                $params += $paramValue
            }
            Invoke-Expression "$command $($params -join ' ')"
        } else {
            Invoke-Expression $command
        }
    }
    Write-Host "Command executed."
    Read-Host "Press Enter to continue..."
}

# Main loop
while ($true) {
    $choice = Show-Menu
    if ($choice -eq ($adbCommands.Count + 1).ToString()) {
        exit
    } elseif ($choice -match '^\d+$' -and [int]$choice -ge 1 -and [int]$choice -le $adbCommands.Count) {
        Run-ADBCommand -index ([int]$choice - 1)
    } else {
        Write-Host "Invalid choice. Please try again."
        Start-Sleep -s 2
    }
}
